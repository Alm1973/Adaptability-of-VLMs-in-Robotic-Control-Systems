# ENTRY 3 — Synthetic vs live: the ordering inverts

| corpus | D_full | F_probe | winner |
|---|---|---|---|
| synthetic (36 ep) | 0.968 / 4 lost | 0.786 / 24 lost | D |
| live (7 occlusion ep) | 0.299 / 160 lost | 0.504 / 98 lost | F |

**Measured cause:** D gives up after `DECAY_FRAMES` = 12. Synthetic
disruptions are 4, 8 or 14 frames. Real occlusions run 40–61 frames.

>>> DRAFT — rewrite in your own words
>>>
>>> - D gives up after 12 frames. Our fake occlusions lasted 4, 8 or 14 frames,
>>>   so in most episodes the timer never ran out and D looked near perfect.
>>>   Real hands cover the cup for 40 to 60 frames, so the timer always runs
>>>   out and D collapses.
>>> - We were testing a 12-frame parameter with tests mostly shorter than 12
>>>   frames. The parameter was never actually exercised.
>>> - This is worse than simulation being optimistic. Optimistic would mean the
>>>   same ranking with inflated scores. Here the ranking reverses, so choosing
>>>   a design on synthetic data selects the one that does worst in reality.
>>> - Lesson to carry: a simulated test has to be at least as hard as the
>>>   parameter it is meant to stress, or it silently measures nothing.

# ENTRY 7 — Timing profile

| stage | calls/frame | ms/call | ms/frame | share |
|---|---|---|---|---|
| detect | 1.00 | 13.9 | 13.92 | 40.9% |
| probe | 0.05 | 270.6 | 13.88 | 40.8% |
| diagnose | 0.39 | 11.7 | 4.56 | 13.4% |
| verify | 0.01 | 181.1 | 1.16 | 3.4% |
| **total** | | | **34.03** | **29.4 fps** |

**Capture rate:** 10.1 fps alone, 8.5 with detector, 3.7 with detector + VLM.
Zero read failures in all conditions.

**Speedups tried and rejected:** fp16 detector — expected 1.5–2×, got 1.03×
with bit-identical outputs. imgsz 640→448 — expected ~2×, got 1.04×. Probe
tokens 12→4 — non-monotonic, therefore noise.

>>> DRAFT — rewrite in your own words
>>>
>>> - The VLM verification call is the most expensive single operation at
>>>   181 ms and accounts for 3.4% of runtime, because it fires about once per
>>>   episode rather than per frame. Cost per call and cost to the system are
>>>   almost unrelated once a call is gated.
>>> - The detector is the opposite: cheap per call at 13.9 ms but runs every
>>>   frame, so it is 40.9%. If we want throughput, that is where it is.
>>> - The token-budget result was non-monotonic — 4 tokens measured slower than
>>>   6. A real effect does not reverse, so that told me it was noise before I
>>>   had an explanation. The explanation came afterwards: generation stops at
>>>   end-of-sequence long before the cap, so lowering the cap cannot save time
>>>   that was never spent.
>>> - Cutting input size from 640 to 448 is 2.3x less compute and gave 1.04x.
>>>   So the detector is not compute-bound at these sizes and roughly 12 ms is
>>>   fixed overhead. No input-size tuning will help.
>>> - The real ceiling is the camera at 10.1 fps against a pipeline that can do
>>>   29.4. Frame rate is a camera setting, not a model setting.

# ENTRY 8 — Search reach limit

**What I found:** the search policy takes 12° steps, 2 per direction — **24°
of reach**. A target lost further away cannot be re-acquired; the policy
exhausts by construction, not because it failed to see anything.

For the nano trials I raised this to 6 steps (72°) so success was possible.
**Not shipped behaviour** — must be labelled in any write-up.

>>> DRAFT — rewrite in your own words
>>>
>>> - No static-camera experiment could have found this, because the arm never
>>>   had to travel. Every earlier test measured whether the system keeps track
>>>   of something it is already looking at.
>>> - 24 degrees is small. If the target ends up 30 degrees off, the robot stops
>>>   searching while the cup is plainly visible from a pose it never reaches —
>>>   and it stops because the policy is exhausted, not because it looked and
>>>   failed to see.
>>> - This also means the earlier synthetic finding that random search beats
>>>   VLM-guided search was measured in a space small enough that the limit
>>>   never mattered.

# ENTRY 11 — The VLM has never steered a search (Assignment 3b)

**Date:** 28 August 2026 · **Hardware:** none · **Script:**
`assignment3b_offline.py` → `assignment3b_offline.json`

**What I set out to do:** the assignment says to amplify the VLM's
directional-search advantage in a cluttered scene. Before booking an attended
hardware session I checked the mechanism offline on frames already on disk.

**There is no advantage to amplify. Two separate faults, either one fatal.**

**Fault 1 — the mechanism is not connected.** `search_direction()` asks
"left, right, up, or down" and reads the answer from `self.verifier`. Since the
speed work, `self.verifier` is `make_fast_verifier()` — a yes/no *logit
comparator* that does not decode text at all.

| what was asked | what came back | what `search_direction()` returns |
|---|---|---|
| "left, right, up, or down" | `'no'` (24/24 frames) | `None` (24/24 frames) |

`'no'` contains none of the four direction words, so the function falls
through to `return None` every time.

**Fault 2 — wired correctly, the answer is a constant.**

| group | n | answers |
|---|---|---|
| clean | 40 | `left` × 40 |
| cluttered | 40 | `left` × 40 |
| **total** | **80** | **`left` 100%** |

**The model is not blind.** Same frames, asked to describe them:
*"A person's hands resting on a keyboard and mouse"*, *"A cluttered desk with
a red cup, coconut water carton..."*. It sees fine. It just answers this
particular question the same way no matter what it sees.

**A test I threw away.** My first version cropped real frames so the cup fell
outside the view and read the true direction off the crop geometry. The cup
sits low in every capture, so the only crop that ever cleared it was the one
above — **120 of 120 trials had ground truth "down"**. Constant truth against
a constant answer measures nothing; had the model's constant been "down" it
would have scored 100%. No accuracy number from that design is reported.

>>> DRAFT — rewrite in your own words
>>>
>>> - The VLM has never chosen a search direction in any run I have recorded.
>>>   Not once. It asks a four-way question of a yes/no comparator, gets "no"
>>>   back, and gives up. Every search result in this project, including the
>>>   nano trials, came from the non-VLM fallback.
>>> - So Entry 5's search numbers are not "the VLM searching". I need to
>>>   restate them as what they are: geometric search with the VLM inert.
>>> - Even if I fix the wiring it still does not work. It says "left" on 80 out
>>>   of 80 real frames from two visibly different scenes. That is a constant,
>>>   not a decision.
>>> - This is the same shape of problem as the OCCLUDER_WORDS string match in
>>>   Entry 9. Both times a capability I attributed to the VLM turned out to be
>>>   a degenerate mechanism that happened to sit in the right place. I should
>>>   say that pattern out loud in the paper — twice is a trend, not bad luck.
>>> - `probe_region` already solved exactly this: it takes a separate
>>>   `probe_verifier` because the fast verifier cannot answer open questions,

## 4(b) False belief is a safety failure, not an accuracy number

**False belief** = the pipeline asserts the target is present when it is not.
Downstream that is a robot reaching for something that is not there.

**Evidence 1 — the substring bug pushed in exactly this direction.**
The old matcher used a plain substring test, so "notebook" matched *book*,
"handbag" matched *hand*, and "armchair" matched *arm*. Every one of those
false matches makes the pipeline conclude *something is covering my cup* and
**hold belief on an absent target**. The bug had a direction, and the
direction was the dangerous one.

**Evidence 2 — accuracy and safety disagree, and accuracy wins the beauty contest.**

| condition | durAcc | **false belief** |
|---|---|---|
| E_no_vlm | **0.923** | **23** |
| D_full | 0.615 | **5** |

The pipeline with the *higher accuracy* asserts a ghost 4.6 times as often.

**Evidence 3 — our current false-belief numbers are near-uninformative.**
In Assignment 2, false belief stayed at exactly 5 for every timer value
**including infinite patience**. Never conceding the cup is gone ought to
produce false belief constantly. It does not, because only 6.0% of scored
frames have the cup absent.

>>> DRAFT — rewrite in your own words
>>>
>>> - False belief is not just another accuracy column. It is the one error
>>>   where the robot does something physical about an object that is not there.
>>>   The other direction — dropping a cup that is really there — costs time.
>>>   This one costs a collision.
>>> - The keyword bug mattered because of its direction, not its size. Every
>>>   wrong match made the system MORE confident about an absent object. A bug
>>>   that erred the other way would have been an annoyance.
>>> - The comparison I keep coming back to: without the VLM the system scores
